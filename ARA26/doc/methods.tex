\section{Methods}

The core of \sysname is a neurosymbolic loop: LLM agents propose decompositions (Thrust~2), a contract engine certifies them (Thrust~1), and its verdicts return to the agents as feedback and rewards (Thrust~3).

\thrust{Thrust 1: Contract Theory for Decomposition.} \sysname decomposes a design along three dimensions. Spatial decomposition splits a system into interacting components, as in our work on architectures~\cite{xiao2024contrarc}, distributed systems~\cite{xiao2026memocode}, and multi-robot systems~\cite{xiao2026acies}. Hierarchical decomposition refines requirements across abstraction levels that use different formalisms. We relate these levels through contract embeddings based on conservative approximations~\cite{naik2024contract}, which map behaviors between formalisms so that a refinement proved on the embedded contracts also holds for the original ones. Temporal decomposition splits a mission into contracts on consecutive time intervals, each handing over to the next and enforced by a time-varying control barrier function, i.e., a certificate that keeps the system inside the states allowed by the contract~\cite{waqas2022cbf}. The contracts themselves are domain-specific. Timing contracts for distributed systems associate the logical ordering of events with execution and communication latencies, and bound the inconsistency and unavailability of each component~\cite{xiao2026memocode}. Robot contracts couple a Generalized Reactivity(1) (GR(1)) mission layer~\cite{bloem2012gr1} with controllers certified by control barrier functions~\cite{ames2019cbf} or reachability analysis. Learned policies, such as \gls{vla} models~\cite{kim2024openvla}, are guarded at run time by safety filters and monitors that report contract violations to the decomposition, and are post-trained with rewards derived from their component contracts. Hardware contracts relate the ports of \gls{rtl} modules over clock cycles.

\thrust{Thrust 2: Agentic Decomposition Search.} \sysname will represent a design as a hierarchy of contracts that LLM agents build recursively, starting from the system requirements. At each level, an agent proposes contracts for the subcomponents, guided by certified decompositions of similar components retrieved from a library of certified contracts (Thrust~3), and the engine accepts the proposal only if the subcomponents together are certified to meet the parent contract. Each accepted subcomponent is either verified directly by a back end or handed to a new agent that works only on its own contract, which keeps the context of every agent small as the design grows. When a component cannot meet its contract, the parent agent revises the decomposition and keeps the certified parts whose contracts are unchanged. Alternative decompositions will be explored by a search in which the agents propose candidates and the engine prunes them. Across domains, only the contract formalism and the back-end tools change, e.g., mixed-integer linear programming for timing contracts, synthesis and reachability tools for robot controllers, and model checkers for hardware.

\thrust{Thrust 3: Learning from Formal Feedback.} Every failed check returns a diagnosis that points to the responsible contract terms: a counterexample trace when refinement or model checking fails, a minimal set of conflicting terms (an unsatisfiable core) when contracts are inconsistent or incompatible, and a minimal set of guarantees that no controller can meet together under the environment assumptions (an unrealizable core) when synthesis fails. Agents call these operations through a \gls{mcp} server, and the engine itself contains no LLM. Repairs take three forms. Formal repair adjusts contract parameters directly, e.g., by tuning inconsistency and unavailability bounds as in~\cite{xiao2026memocode}. Agent repair returns the diagnosis to the agent. Pattern-based repair generalizes recurring failures into patterns stored in a pattern library. When adding components cannot remove a failure, e.g., inconsistent guarantees, its pattern excludes every candidate that contains it, as detected by subgraph isomorphism~\cite{xiao2024contrarc}. Certified contracts are stored in a contract library for retrieval, so that both libraries grow with each design. Finally, an open-weight proposer is post-trained by reinforcement learning on its own proposals with verifiable rewards, i.e., rewards computed by the engine, which grades each proposal by the consistency, refinement, and realizability of its component contracts. Trivial decompositions and timeouts earn no reward. Soundness never depends on the proposer.

\thrust{Evaluation and preliminary results.} Our prior work improves the reliability of auto-formalization by screening diverse candidate formalizations with solvers~\cite{ni2026draftprune} and assesses reasoning agents with solver-backed checks~\cite{ni2026agentified}, principles that \sysname applies to contracts. For distributed systems, our timing contracts~\cite{xiao2026memocode} verified and repaired the consistency and availability requirements of an automatic emergency braking system and a multi-drone coordination scenario. In multi-robot systems, ACIES~\cite{xiao2026acies} decomposes mission requirements into GR(1) contracts, synthesizes controllers, and executes them under control barrier functions, and our ongoing work extends it with runtime monitors and a library of certified components. In hardware, component contracts are written as \glspl{sva} and proved by hardware model checkers on open designs such as OpenTitan. We will compare frontier models with and without formal feedback and retrieval against the post-trained proposer, including on faulty RTL designs, measuring the requirements certified beyond direct checking, the acceptance rate, solver runs and tokens per certificate, library reuse, and contract violations of post-trained \gls{vla} policies.
