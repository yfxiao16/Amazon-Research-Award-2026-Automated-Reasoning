\section{Methods}

The core of \sysname is a neurosymbolic loop: LLM agents propose decompositions (Thrust~2), a contract engine certifies them on the theory of Thrust~1, and its verdicts return to the agents in context and as post-training rewards (Thrust~3). We will evaluate it on distributed systems, multi-robot control, and hardware.

\thrust{Thrust 1: Contract Theory for Decomposition.} \sysname decomposes a design along three dimensions. Spatial decomposition splits a system into interacting components, as in our work on architectures~\cite{xiao2024contrarc}, distributed systems~\cite{xiao2026memocode}, and multi-robot control~\cite{xiao2026acies}. Hierarchical decomposition refines requirements across abstraction levels that use different formalisms, which we relate through contract embeddings based on conservative approximations~\cite{naik2024contract}, which map behaviors between formalisms so that a refinement proved on the embedded contracts also holds for the original ones. Temporal decomposition splits a mission into contracts on non-overlapping time intervals, each enforced by a time-varying control barrier function, i.e., a certificate that keeps the system inside the states allowed by the contract~\cite{waqas2022cbf}. The contracts themselves are domain-specific. Timing contracts for distributed systems associate the logical ordering of events with execution and communication latencies, and bound the inconsistency and unavailability of each component~\cite{xiao2026memocode}. Robot contracts couple a mission layer in Generalized Reactivity(1) (GR(1)) logic~\cite{bloem2012gr1} with controllers certified by control barrier functions~\cite{ames2019cbf} or reachability analysis. Learned policies, such as \gls{vla} models~\cite{kim2024openvla}, are guarded at run time by safety filters and monitors that report violated assumptions to the decomposition, and are post-trained with rewards derived from their component contracts. Hardware contracts relate the ports of register-transfer-level modules over clock cycles.

\thrust{Thrust 2: Agentic Decomposition Search.} \sysname will represent a design as a hierarchy of contracts that LLM agents build recursively, starting from the system requirements. At each level, an agent proposes contracts for the subcomponents, guided by certified decompositions of similar components retrieved from the contract library, and the engine accepts the proposal only if the subcomponents together are certified to meet the parent contract. Each accepted subcomponent is either verified directly by a back end or handed to a new agent that works only on its own contract, which keeps the context of every agent small as the design grows. When a component cannot meet its contract, the failure is reported to its parent, which revises the decomposition while keeping the certified parts. Alternative decompositions will be explored by a search in which the agents propose candidates and the engine prunes them. Across domains, only the back-end verification tools change, e.g., mixed-integer linear programming for timing contracts, synthesis and reachability tools for robot controllers, and model checkers for hardware modules.

\thrust{Thrust 3: Learning from Formal Feedback.} Every failed check returns a diagnosis that points to the responsible contract terms: a counterexample trace when refinement or model checking fails, a minimal set of conflicting terms (an unsatisfiable core) when contracts are inconsistent, and a minimal set of requirements that no controller can meet together (an unrealizable core) when synthesis fails. Agents call these operations through a \gls{mcp} server, while no LLM is part of the engine. Repairs are then attempted in three ways. Formal repair adjusts contract parameters directly, e.g., by tuning inconsistency and unavailability bounds as in~\cite{xiao2026memocode}. Agent repair returns the diagnosis to the agent. Pattern-based repair generalizes recurring failures into repair patterns that, through subgraph isomorphism~\cite{xiao2024contrarc}, exclude every candidate containing the same failing structure, and records them in a pattern library. Certified contracts are stored in a contract library, so that the framework evolves with each design: the decomposer retrieves certified decompositions from it, while search and verification reuse the pattern library. Finally, certified decompositions are used to post-train an open-weight proposer, with the checks of the engine as verifiable rewards, i.e., rewards computed by a checker, graded by the consistency, refinement, and realizability of each component contract. As the engine checks every proposal, soundness never depends on the proposer.

\thrust{Evaluation and preliminary results.} Our prior work improves the reliability of auto-formalization by screening diverse candidate formalizations with solvers~\cite{ni2026draftprune} and assesses reasoning agents with solver-backed checks~\cite{ni2026agentified}, principles that \sysname applies to contract generation and revision. For distributed systems, our timing contracts~\cite{xiao2026memocode} verified and repaired the consistency and availability requirements of an automatic emergency braking system and a multi-drone coordination scenario. In multi-robot control, ACIES~\cite{xiao2026acies} decomposes mission requirements into GR(1) contracts, synthesizes controllers, and executes them under control barrier functions, and our ongoing work extends it with runtime monitors and a library of certified components. In hardware, component contracts are \glspl{sva} with ghost-state models, discharged by hardware model checkers. Our prototype certified an end-to-end in-order delivery property of an asynchronous link from the HierSVA benchmark~\cite{nie2026hiersva} with 25 model-checking runs and about 16,000 LLM input tokens, while direct model checking of the end-to-end property did not finish within a considerably longer time limit. The decomposition found at FIFO depth 8 certified depths 16 to 512 with no further LLM calls, and an agent without the protocol used 24 times as many tokens without completing the proof. We will compare frontier models with and without formal feedback and retrieval against the post-trained proposer, measuring the requirements certified beyond direct verification or synthesis, the acceptance rate, and solver runs and tokens per certificate.
